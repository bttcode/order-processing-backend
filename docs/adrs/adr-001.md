# ADR-001: Database Selection, Primary Key Strategy, and Product ID Resolution

## Status

Accepted

## Context

Three decisions were deferred or left ambiguous in the initial schema design
(`04-database.md § DB-1`) and must be resolved before Phase 1 implementation
begins. They are grouped in a single ADR because they interact: the choice of
database constrains the PK type options, and the PK type choice on `orders`
directly affects the FK type on `order_items`, which in turn touches the
unresolved `[OI-12]` question about `products.id`.

### Problem 1 — Database engine

The system targets 10,000+ orders/sec with sub-100ms p99 latency, zero
overselling, and ACID compliance for all order + inventory writes. Two
candidates were considered.

### Problem 2 — `orders` primary key

The original schema uses `UUID PRIMARY KEY DEFAULT gen_random_uuid()` (UUIDv4).
At 10k inserts/sec, UUIDv4's random distribution causes B-tree page splits on
every insert because new keys land at random leaf positions. The clustered index
fragments rapidly. The `order_items` FK references this PK on every insert too,
so the fragmentation cost is paid twice per order.

The alternative — UUIDv7 — is time-ordered (ms-precision timestamp in the high
bits) and is therefore monotonically increasing within a millisecond window,
which makes B-tree insertions sequential. However, using UUIDv7 directly as the
clustered PK still costs 128 bits per FK reference, and exposes timing
information in the public API: the `orderId` returned to callers would allow
enumeration of order creation timestamps and approximate volume inference.

### Problem 3 — `products` primary key and the `order_items` FK (OI-12)

`products.id` is `VARCHAR(50)`. Every inventory reservation under `FR-2` and
`FR-3` executes a join `order_items.product_id → products.id`. At 10k orders/sec
with an average of 2 items per order, this join runs ~20,000 times per second.
`VARCHAR(50)` comparison is slower than integer comparison, the column is wider
(up to 50 bytes vs 8 bytes for `BIGINT`), and the FK index on `order_items`
carries that width penalty in every index entry. The `[OI-12]` note deferred
this to Phase 3 profiling, but the schema must be correct from Phase 1 — fixing
a PK after data exists requires a table rewrite and is far more disruptive than
deciding upfront.

### Constraints

- PostgreSQL 15 is mandated (`00-overview.md § TR-1`); `gen_uuid_v7()` is only
  available natively from PostgreSQL 17.
- The domain model in `domain/model/Order.java` and `domain/model/Product.java`
  must not be polluted with infrastructure concerns (`pk`, surrogate keys).
- The public API (`05-api.md § API-1`) exposes `orderId` and `productId` in
  responses and URLs — those identifiers must be stable and safe for external
  consumption.
- `[OI-12]` explicitly forbids changing the schema without an ADR.

## Decision

### 1 — Database: PostgreSQL 15

PostgreSQL is selected as the sole primary database.

### 2 — `orders` table: BIGSERIAL surrogate PK + UUIDv7 public handle

The `orders` table uses **two identifiers with distinct responsibilities**:

| Column | Type | Role |
|--------|------|------|
| `pk` | `BIGSERIAL` | Internal clustered PK — never leaves the infrastructure layer |
| `id` | `UUID NOT NULL UNIQUE` | Public handle — used in all API responses and URLs |

`id` is populated with UUIDv7 generated in application code before persistence.
`pk` is generated by PostgreSQL via `IDENTITY`. All FK references from
`order_items` use the `BIGINT pk`, not the UUID.

### 3 — `products` table: BIGSERIAL surrogate PK + preserved string business key

The `products` table adopts the same two-identifier pattern:

| Column | Type | Role |
|--------|------|------|
| `pk` | `BIGSERIAL` | Internal clustered PK — used as FK target in `order_items` |
| `id` | `VARCHAR(50) NOT NULL UNIQUE` | Business/public identifier (e.g. `PROD-001`) |

The `order_items.product_pk` FK references `products.pk` (`BIGINT`), replacing
the original `order_items.product_id VARCHAR(50)` FK. The `product_id` column
is retained in `order_items` as a **denormalised snapshot** of the business key
at order creation time (preserves historical accuracy if a product is later
renamed or deleted).

## Rationale

### Why PostgreSQL over MongoDB

| Criterion | PostgreSQL | MongoDB |
|-----------|-----------|---------|
| ACID transactions across tables | Full — required for BR-3 (atomic inventory) | Document-level only; multi-document transactions added in 4.0 but carry significant overhead |
| Optimistic locking via `@Version` | Native support — Hibernate issues `WHERE version = ?` on UPDATE | No equivalent; requires application-level CAS with `findOneAndUpdate` |
| Isolation levels | All four levels — REPEATABLE_READ required for `AR-4` | Snapshot isolation only |
| Joins | Native — `order_items`, inventory checks, composite queries all require them | Discouraged; embedding denormalises aggressively |
| Schema validation | DDL constraints + check constraints — enforced at DB level | JSON schema validation — optional and application-enforced |
| Tooling maturity for Spring | Spring Data JPA + Hibernate 6.x — first-class support, `@Transactional` works as expected | Spring Data MongoDB — no JPA, no `@Version` optimistic locking, no isolation levels |

MongoDB was rejected because the core correctness requirements (BR-3 zero
overselling, BR-5 idempotency, ACID order + inventory atomicity) rely on
multi-table transactions with repeatable-read isolation. These are straightforward
in PostgreSQL and require complex workarounds in MongoDB that would obscure the
learning objectives of the project.

### Why BIGSERIAL surrogate PK on `orders` instead of UUIDv7 as PK

**Option A — UUIDv4 as PK (original schema):**
Random inserts into a B-tree cause a page split on roughly every other insert
once the index is large. At 10k orders/sec on a 100k-row table, the planner
must read a random leaf page for each insert, evicting cached pages. This
directly harms the p99 latency target. Additionally, the `order_items` FK is
128 bits wide, occupying more index space than necessary.

**Option B — UUIDv7 as PK:**
Time-ordered within a millisecond, so inserts are nearly sequential —
substantially better than UUIDv4. However: (1) UUID is 128 bits; BIGINT is 64
bits — the FK in `order_items` is half the width with BIGINT, which matters at
20k+ FK index entries per second; (2) the clustered PK value would be visible if
ever exposed accidentally — with a surrogate BIGINT PK the UUID column is the
only identifier that reaches external systems; (3) PostgreSQL 15 has no native
`gen_uuid_v7()` — a PL/pgSQL function or application-side generation is required
regardless, so there is no simplicity advantage to keeping it as the PK.

**Option C — BIGSERIAL PK + UUIDv7 public handle (chosen):**
- `BIGSERIAL` inserts are always sequential — zero page splits, maximum cache
  locality on the clustered index.
- The `order_items` FK is `BIGINT` — 8 bytes per entry, smaller index, faster
  join.
- UUIDv7 in the `id` column is still time-ordered, so the UNIQUE index on it is
  also sequential — no fragmentation on that index either.
- Timing leakage from UUIDv7 is acceptable here: the API already returns
  `createdAt` in every response, so the timestamp is not new information. Cross-
  customer enumeration is blocked by ownership checks enforced in the use-case
  layer, not by ID obscurity.
- The domain model sees only `UUID id` — the `BIGINT pk` never crosses into
  `domain/` or `application/`. This preserves the hexagonal boundary.

**Option D — BIGSERIAL PK + UUIDv4 public handle:**
Viable. The only loss vs UUIDv7 is that the UNIQUE index on the `id` column
fragments (random inserts). At the write volume of this system (~10k/sec on
`orders`) this index will fragment noticeably. UUIDv7 avoids this at no
additional complexity cost once the generator is in place.

### Why surrogate PK on `products` (resolving OI-12)

**Option A — Keep VARCHAR(50) as PK (original schema):**
The FK `order_items.product_id → products.id` executes on every inventory
reservation. VARCHAR comparison requires a byte-by-byte scan up to 50 bytes;
BIGINT comparison is a single 64-bit integer operation. The FK index entries in
`order_items` are also 50 bytes wide instead of 8 bytes, increasing the index
size by ~6× for that column. At 20k FK lookups/sec this is measurable.

**Option B — BIGSERIAL surrogate PK + VARCHAR(50) business key (chosen):**
- `order_items.product_pk` FK becomes `BIGINT` — narrow, fast, cache-friendly.
- `products.id` (the business key, e.g. `PROD-001`) is retained as a
  `UNIQUE NOT NULL` column — lookup by business key still works via a dedicated
  index.
- `order_items` retains a denormalised `product_id VARCHAR(50)` column as a
  **snapshot** — this is not a FK; it records what the product ID was at order
  creation time, independent of future product changes.
- The domain model `Product.java` exposes `String id` (the business key) —
  `Long pk` stays in `ProductEntity`. The domain never sees the surrogate.

**Option C — Hash index on VARCHAR(50) PK:**
Suggested in `[OI-12]`. A hash index on the PK speeds up equality lookups but:
(1) PostgreSQL hash indexes are not crash-safe before PG10 (not an issue on
PG15, but worth knowing); (2) the FK index on `order_items` must be a B-tree
regardless — the width problem in `order_items` is not solved by changing the
index type on `products`; (3) range scans and ORDER BY on the product PK
(needed for sorted admin queries) cannot use a hash index. Rejected.

## Consequences

### What becomes easier

- **Insert throughput:** Sequential BIGSERIAL PK eliminates B-tree page splits
  on all hot write tables. The `orders` and `products` clustered indexes remain
  dense regardless of write volume.
- **Join performance:** `order_items → orders` and `order_items → products` FKs
  are both `BIGINT` — 8-byte comparisons, smaller index pages, higher cache hit
  rate.
- **Adapter swap:** The `BIGINT pk` is fully contained in `OrderEntity` and
  `ProductEntity`. Swapping the JPA adapter for an in-memory adapter (DEL-1 in
  `07-delivery.md`) requires no domain model changes.
- **API stability:** UUIDv7 `id` values are stable external identifiers. They
  can appear in URLs, be stored by clients, and be used in idempotency keys
  without coupling clients to internal row numbering.

### What becomes harder

- **Schema complexity:** Each table has two identifiers instead of one. Flyway
  migrations, JPA entities, and mapper classes must be consistent. A developer
  who forgets to set `id` before saving an `OrderEntity` will get a NOT NULL
  violation at runtime — add a `@PrePersist` guard.
- **UUIDv7 generation on PG15:** No native function. Application must generate
  UUIDv7 before insert. The `OrderIdGenerator` utility is a new infrastructure
  class that must be tested in isolation.
- **Query by public ID:** `GET /orders/{orderId}` queries by UUID `id`, not by
  `pk`. The JPA repository needs `findByPublicId(UUID id)` which hits the UNIQUE
  index on `id`, not the PK index. This is one index hop, not a PK lookup.
  Acceptable, but must be verified with `EXPLAIN ANALYZE` in Phase 3.
- **`order_items` dual product columns:** Both `product_pk BIGINT` (FK) and
  `product_id VARCHAR(50)` (snapshot) exist. The FK is for integrity; the
  snapshot is for historical accuracy. Any query joining `order_items` to
  `products` must use `product_pk`, not `product_id`. This must be enforced
  in code review and documented in schema notes.

### New risks

- `OrderIdGenerator` is a stateless utility wrapping a time-based UUID library.
  If two JVM instances generate UUIDs at the exact same millisecond, there is
  no collision — UUIDv7 includes 12 bits of random sub-millisecond data. Risk
  is negligible but the library choice must guarantee this.
- `pk` leakage: if a developer adds `pk` to a DTO or logs it, the sequential
  nature exposes order volume. Add a Checkstyle or ArchUnit rule that prevents
  `pk` from appearing in any class outside `infrastructure/persistence/`.

## Implementation Notes

### Flyway migration V1 — revised DDL

```sql
-- V1__initial_schema.sql

-- orders: surrogate BIGINT PK + UUIDv7 public handle
CREATE TABLE orders (
    pk                     BIGINT        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id                     UUID          NOT NULL,
    customer_id            VARCHAR(50)   NOT NULL,
    status                 VARCHAR(30)   NOT NULL,
    total_amount           DECIMAL(12,2) NOT NULL,
    currency               VARCHAR(3)    NOT NULL DEFAULT 'USD',
    payment_method         VARCHAR(20),
    payment_transaction_id VARCHAR(100),
    idempotency_key        UUID          UNIQUE,
    created_at             TIMESTAMP     NOT NULL DEFAULT NOW(),
    updated_at             TIMESTAMP     NOT NULL DEFAULT NOW(),
    confirmed_at           TIMESTAMP,
    version                INTEGER       NOT NULL DEFAULT 0,

    CONSTRAINT uq_orders_id UNIQUE (id),
    CONSTRAINT chk_order_status CHECK (status IN (
        'PENDING_VALIDATION','PENDING_PAYMENT','PAYMENT_AUTHORIZED',
        'CONFIRMED','CANCELLED','INSUFFICIENT_INVENTORY','PAYMENT_FAILED'
    ))
);

-- products: surrogate BIGINT PK + VARCHAR(50) business key
CREATE TABLE products (
    pk                 BIGINT        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id                 VARCHAR(50)   NOT NULL,
    sku                VARCHAR(100)  NOT NULL,
    name               VARCHAR(200)  NOT NULL,
    description        TEXT,
    price              DECIMAL(12,2) NOT NULL,
    inventory_quantity INTEGER       NOT NULL DEFAULT 0,
    version            INTEGER       NOT NULL DEFAULT 0,
    created_at         TIMESTAMP     NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT uq_products_id  UNIQUE (id),
    CONSTRAINT uq_products_sku UNIQUE (sku),
    CONSTRAINT chk_price       CHECK (price >= 0),
    CONSTRAINT chk_inventory   CHECK (inventory_quantity >= 0)
);

-- order_items: FK on BIGINT pk, plus denormalised product_id snapshot
CREATE TABLE order_items (
    id            BIGSERIAL     PRIMARY KEY,
    order_pk      BIGINT        NOT NULL REFERENCES orders(pk) ON DELETE CASCADE,
    product_pk    BIGINT        NOT NULL REFERENCES products(pk),
    product_id    VARCHAR(50)   NOT NULL,   -- snapshot: business key at order time
    product_name  VARCHAR(200)  NOT NULL,   -- snapshot: name at order time
    quantity      INTEGER       NOT NULL,
    unit_price    DECIMAL(12,2) NOT NULL,
    total_price   DECIMAL(12,2) NOT NULL,

    CONSTRAINT chk_quantity CHECK (quantity > 0)
);

-- idempotency_keys: UUID PK is appropriate here — keys are externally supplied
CREATE TABLE idempotency_keys (
    key             UUID      PRIMARY KEY,
    response_body   TEXT      NOT NULL,
    response_status INTEGER   NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMP NOT NULL
);

-- Index block (single source of truth per OI-10)

-- orders access patterns
CREATE UNIQUE INDEX idx_orders_public_id     ON orders(id);
CREATE INDEX        idx_order_customer_date  ON orders(customer_id, created_at DESC);
CREATE INDEX        idx_order_status         ON orders(status)
    WHERE status NOT IN ('CONFIRMED','CANCELLED');
CREATE INDEX        idx_order_idempotency    ON orders(idempotency_key);
CREATE INDEX        idx_order_composite      ON orders(customer_id, status, created_at DESC);

-- products access patterns
CREATE UNIQUE INDEX idx_products_business_id ON products(id);
CREATE UNIQUE INDEX idx_products_sku         ON products(sku);

-- order_items access patterns
CREATE INDEX idx_order_item_order_pk   ON order_items(order_pk);
CREATE INDEX idx_order_item_product_pk ON order_items(product_pk);
-- Retained for snapshot queries (e.g. "all items for product PROD-001 ever ordered")
CREATE INDEX idx_order_item_product_id ON order_items(product_id);

-- idempotency cleanup
CREATE INDEX idx_idempotency_expires ON idempotency_keys(expires_at);
```

> Note: `GENERATED ALWAYS AS IDENTITY` is the SQL-standard equivalent of
> `BIGSERIAL` and is preferred in PostgreSQL 10+. It prevents application code
> from accidentally overriding the sequence value, which `BIGSERIAL` allows.

### UUIDv7 generator (application layer)

Add the `java-uuid-generator` library (Jackson's UUID library, actively
maintained, zero extra dependencies beyond what Spring Boot already pulls in):

```xml
<!-- pom.xml -->
<dependency>
    <groupId>com.fasterxml.uuid</groupId>
    <artifactId>java-uuid-generator</artifactId>
    <version>4.3.0</version>
</dependency>
```

```java
// infrastructure/persistence/util/OrderIdGenerator.java
package com.example.orderprocessing.infrastructure.persistence.util;

import com.fasterxml.uuid.Generators;
import com.fasterxml.uuid.impl.TimeBasedEpochGenerator;

import java.util.UUID;

/**
 * Generates UUIDv7 identifiers for use as the public order handle.
 * UUIDv7 embeds a millisecond-precision Unix timestamp in the high bits,
 * making values monotonically increasing within a millisecond window.
 * The remaining 74 bits are random, ensuring uniqueness across concurrent
 * JVM instances without coordination.
 *
 * This class is infrastructure — it must not be imported by domain or
 * application layers.
 */
public final class OrderIdGenerator {

    // TimeBasedEpochGenerator is thread-safe; single shared instance is correct.
    private static final TimeBasedEpochGenerator GENERATOR =
        Generators.timeBasedEpochGenerator();

    private OrderIdGenerator() {}

    public static UUID generate() {
        return GENERATOR.generate();
    }
}
```

### JPA entities

```java
// infrastructure/persistence/jpa/OrderEntity.java
@Entity
@Table(name = "orders")
public class OrderEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "pk", insertable = false, updatable = false)
    private Long pk;                         // never exposed outside infrastructure

    @Column(name = "id", nullable = false, unique = true, updatable = false)
    private UUID id;                         // UUIDv7 — set by application before save

    @Column(name = "customer_id", nullable = false)
    private String customerId;

    @Column(name = "status", nullable = false)
    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    @Version
    @Column(name = "version", nullable = false)
    private Integer version;

    // ... remaining columns

    @PrePersist
    void ensurePublicId() {
        // Guard: if caller forgot to set id, generate one rather than hitting
        // a NOT NULL violation with an unhelpful DB error message.
        if (this.id == null) {
            this.id = OrderIdGenerator.generate();
        }
    }
}

// infrastructure/persistence/jpa/ProductEntity.java
@Entity
@Table(name = "products")
public class ProductEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "pk", insertable = false, updatable = false)
    private Long pk;

    @Column(name = "id", nullable = false, unique = true, updatable = false)
    private String id;                       // business key, e.g. "PROD-001"

    @Column(name = "inventory_quantity", nullable = false)
    private Integer inventoryQuantity;

    @Version
    @Column(name = "version", nullable = false)
    private Integer version;

    // ... remaining columns
}

// infrastructure/persistence/jpa/OrderItemEntity.java
@Entity
@Table(name = "order_items")
public class OrderItemEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // FK to orders.pk — BIGINT, fast join
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_pk", nullable = false)
    private OrderEntity order;

    // FK to products.pk — BIGINT, fast join
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_pk", nullable = false)
    private ProductEntity product;

    // Denormalised snapshot — NOT a FK, captured at order creation time
    @Column(name = "product_id", nullable = false, updatable = false)
    private String productId;               // e.g. "PROD-001"

    @Column(name = "product_name", nullable = false, updatable = false)
    private String productName;

    @Column(name = "quantity", nullable = false)
    private Integer quantity;

    @Column(name = "unit_price", nullable = false)
    private BigDecimal unitPrice;

    @Column(name = "total_price", nullable = false)
    private BigDecimal totalPrice;
}
```

### JPA adapter — lookup by public ID

```java
// infrastructure/persistence/jpa/JpaOrderRepository.java (Spring Data)
public interface JpaOrderRepository extends JpaRepository<OrderEntity, Long> {
    // PK-based ops use the BIGINT pk automatically (JpaRepository<..., Long>)
    Optional<OrderEntity> findByPublicId(UUID id); // → WHERE id = ?  (UNIQUE index)
}

// infrastructure/persistence/OrderJpaAdapter.java
@Repository
public class OrderJpaAdapter implements OrderRepository {

    private final JpaOrderRepository jpaRepo;
    private final OrderMapper mapper;

    @Override
    public Optional<Order> findById(UUID publicId) {
        return jpaRepo.findByPublicId(publicId).map(mapper::toDomain);
    }

    @Override
    public Order save(Order order) {
        OrderEntity entity = mapper.toEntity(order);
        // id is set by mapper from domain Order.id (UUIDv7, already generated)
        OrderEntity saved = jpaRepo.save(entity);
        return mapper.toDomain(saved);
    }
}
```

not `Seq Scan`, at 100k+ rows:

## Related ADRs

- **ADR-003** (Inventory Locking — Optimistic vs Pessimistic): relies on
  `@Version` on `ProductEntity` as established here; the surrogate PK does not
  affect locking behaviour but the entity structure defined here is the
  foundation ADR-003 builds on.
- **ADR-005** (Transaction Propagation Strategy): `REQUIRES_NEW` on the audit
  service commits independently of the parent order transaction; the identity
  columns here mean the `pk` is available as soon as the INSERT completes,
  regardless of whether the outer transaction commits.
- **ADR-008** (API Versioning): v1 and v2 both expose `orderId` as the UUID
  public handle; the `pk` must not appear in either version's DTO.
