# ADR-002: Concurrency Model — Reactive vs Thread-per-Request

## Status
Accepted

## Context
Phase 2 requires: parallel inventory checks across multiple products per order
(FR-2), payment authorization with a 5-second hard timeout (FR-3), and the
ability to sustain 10,000 orders/sec with p99 < 100ms (NFR-1). The two
candidate models are:

**Thread-per-request (synchronous):** Each HTTP request occupies one platform
thread for its full duration. Simple to reason about and to debug; naturally
integrates with `@Transactional` and Spring's synchronous data access stack
(Spring Data JPA + Hibernate). At 10k concurrent requests this requires 10k
live threads; JVM overhead is measurable (~1 MB stack per thread by default).

**Reactive (Project Reactor Mono/Flux):** Event-loop-based; a small fixed
thread pool drives many concurrent requests. Blocking calls (DB, payment
gateway) must be moved off the event-loop to a bounded elastic thread pool.
Dramatically reduces thread count under load. Requires `@Transactional`
semantics to be re-implemented explicitly (Spring Data R2DBC or explicit
`TransactionalOperator`); every code path must be non-blocking or explicitly
offloaded.

A third hybrid option was considered: keep the Spring MVC blocking stack but
add an internal reactive pipeline for the sub-pipeline (inventory + payment)
only. This is the approach taken here.

## Decision

**Hybrid model:**

- Spring MVC (Servlet stack, thread-per-request) for the HTTP layer.
  Controllers remain synchronous; the Servlet container manages the thread pool.
- Inside `OrderService`, two execution paths coexist:
    1. `createOrder(command)` — fully synchronous; used by the REST controller
       in Phase 2. Integrates cleanly with `@Transactional`.
    2. `processOrderReactive(command)` — `Mono<Order>` reactive pipeline that
       wraps all blocking calls in `Mono.fromCallable(...).subscribeOn(boundedElastic)`.
       Wired for the Phase 3 performance comparison (PER-2 measurement table).
- Two named `ThreadPoolExecutor` beans replace the default Spring thread pool
  for domain work:
    - `orderProcessingExecutor` (core=8, max=16, CallerRunsPolicy) — general orchestration.
    - `inventoryCheckExecutor` (core=4, max=8, AbortPolicy) — inventory fan-out.

The reactive path uses `Schedulers.boundedElastic()` for all blocking I/O,
keeping the Reactor event-loop threads free. Full R2DBC migration is deferred
until Phase 4's architecture refactor; transactional correctness in Phase 2
is preserved by the synchronous path.

## Rationale

**Why not pure reactive now?**
`@Transactional` with Hibernate and synchronous JDBC is the correctness
foundation for inventory locking and payment idempotency. Migrating to R2DBC
in Phase 2 would couple infrastructure changes (reactive drivers, R2DBC
repositories) with the concurrency changes, making both harder to reason about
and test in isolation. The hybrid approach delivers the observable performance
improvement (parallel inventory fan-out, non-blocking payment timeout) without
dismantling the transactional guarantees.

**Why CallerRunsPolicy on orderProcessingExecutor?**
When the queue fills (1000 tasks), the HTTP thread itself runs the submitted
task rather than dropping it. This provides implicit backpressure: the HTTP
connector slows down accepting new connections, which propagates upstream to
the load balancer / client. Orders are never silently dropped.

**Why AbortPolicy on inventoryCheckExecutor?**
Inventory checks are short-lived fan-out tasks (one per product, parallel).
If the executor is saturated, the system is already overloaded; throwing
`RejectedExecutionException` fast is safer than queueing indefinitely. The
caller catches this and transitions the order to `INSUFFICIENT_INVENTORY`,
which is a recoverable client-side retry.

**Why [OI-7] matters here:**
`CallerRunsPolicy` (executor level) and `RateLimitInterceptor` (HTTP edge)
are complementary, not duplicates. Rate limiter rejects early; CallerRunsPolicy
throttles inside. Both must be tested in TEST-3 Scenario 4 (spike test).

## Consequences

**Easier:**
- `@Transactional` continues to work correctly on the synchronous path —
  no transaction propagation surprises.
- The reactive path in `processOrderReactive` can be benchmarked in Phase 3
  against the synchronous path to generate the PER-2 comparison table.
- Inventory fan-out via `CompletableFuture.allOf()` is straightforward and
  independently testable without a running Reactor context.

**Harder:**
- `@Transactional` does not propagate across reactive thread boundaries. Each
  `Mono.fromCallable(...)` block in `processOrderReactive` runs in its own
  transaction. A failure mid-pipeline requires explicit compensating actions
  (inventory release) rather than relying on a single transaction rollback.
- The `Thread.sleep()` inside `RetryAspect` must not appear inside the reactive
  pipeline (OI-9). A compiler guard is impractical; the constraint is enforced
  by code review and documented in every call site.
- Phase 4 must decide whether to commit to reactive-everywhere (R2DBC) or
  stay hybrid and accept the two-path maintenance cost.

## Implementation Notes

Key classes:
- `ExecutorConfiguration` — defines both `ThreadPoolExecutor` beans.
- `InventoryService.checkAvailabilityParallel` — fan-out with `CompletableFuture.allOf`.
- `OrderService.processOrderReactive` — the Reactor pipeline.
- `RetryAspect` — synchronous retry only; see OI-9.

Performance baseline data is recorded after Phase 3 load tests and appended
to `docs/PERFORMANCE.md`.
