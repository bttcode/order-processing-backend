# ADR-003: Inventory Locking — Optimistic vs Pessimistic

## Status
Accepted

## Context
Inventory reservation (FR-2, BR-3) is the hardest correctness problem in the
system: at 10,000 orders/sec, many concurrent requests may try to decrement the
same product's stock simultaneously. The database must prevent overselling
(inventory_quantity < 0) regardless of concurrency level.

Two primary candidates:

**Pessimistic locking (`SELECT … FOR UPDATE`):** The first transaction to read
the product row acquires an exclusive lock; all other transactions block until
the lock is released. Guarantees no conflict by serialising writers.

**Optimistic locking (`@Version`):** No lock is acquired at read time. When a
transaction tries to commit its UPDATE it checks whether the version column has
changed since the row was read; if another transaction committed first, Hibernate
throws `OptimisticLockException` and the caller retries.

## Decision

**Optimistic locking with `@Version` and a 3-attempt retry.**

- `ProductEntity` carries a `@Version Integer version` field.
- `InventoryService.reserveInventory` is annotated
  `@Transactional(isolation = Isolation.REPEATABLE_READ)`.
- `@Retryable(on = OptimisticLockException.class, maxAttempts = 3, delayMs = 50)`
  is applied to the same method; `RetryAspect` re-invokes the method (re-reads
  the product, re-checks stock, re-saves) on each conflict.
- After 3 failed attempts the `OptimisticLockException` propagates to
  `OrderService`, which transitions the order to `INSUFFICIENT_INVENTORY`.

## Rationale

**Why not pessimistic locking?**

| Criterion | Pessimistic | Optimistic (chosen) |
|-----------|------------|---------------------|
| Throughput under low contention | Lower — lock acquisition on every read even when no conflict | Higher — no lock unless two writes collide |
| Throughput under high contention | Degrades — all writers queue behind the lock holder | Degrades gracefully — contention causes retries, not deadlocks |
| Deadlock risk | Real — two transactions locking different products in different orders can deadlock | None — no locks held |
| Implementation complexity | Simple but hides performance cost | Requires retry logic |
| Connection pool pressure | Lock-waiting transactions hold connections open | Retrying transactions release and re-acquire connections between attempts |

At 10k orders/sec the majority of orders target different products; contention
on any single product is the exception, not the rule. Optimistic locking avoids
paying the lock-acquisition cost on every read and allows true parallelism across
non-overlapping product sets.

Pessimistic locking would be preferred for a warehouse system where every
picking station updates the same small set of bins. This is a high-SKU
e-commerce system — a different access pattern.

**Why `REPEATABLE_READ`?**
Without `REPEATABLE_READ`, a transaction could read inventory = 100, another
transaction could commit a deduction to 85, and the first transaction would
then see 100 (stale) on a second read within the same transaction — a
non-repeatable read. With `REPEATABLE_READ`, a transaction's view of any row
is frozen to the snapshot taken at its first read. Hibernate's version check
then correctly detects that the committed version is higher than the read
version and throws `OptimisticLockException`.

**[OI-8] Explicit isolation requirement:**
`REPEATABLE_READ` must be set on `@Transactional(isolation = Isolation.REPEATABLE_READ)`.
It is NOT inherited from a parent `READ_COMMITTED` transaction. PostgreSQL's
default isolation is `READ_COMMITTED`; a nested call inherits the parent's
connection and isolation, but Spring's `REQUIRED` propagation reuses the parent
transaction without re-setting its isolation level. The `@Transactional` on
`reserveInventory` sets the isolation explicitly by beginning a new connection-
level transaction attribute when the method runs.

This is verified by DB-3 Test 2 (see `04-database.md`).

## Consequences

**Easier:**
- No deadlock risk — retries are bounded and predictable.
- Free parallelism: orders for different products run concurrently without
  blocking each other.
- `@Version` is a single integer column on `ProductEntity` — zero schema impact
  beyond the column already present.

**Harder:**
- Under extreme contention (many threads hitting the same product), retry storms
  can amplify load. The 50ms linear back-off reduces this; Phase 3 load tests
  measure retry rates in practice.
- Retry logic must be instrumented (Micrometer counter: `inventory.lock.retries`)
  so operations engineers can detect contention hotspots. Not wired in Phase 2 —
  added in Phase 3.
- The `@Retryable` / `RetryAspect` retry path uses `Thread.sleep()` — see OI-9
  and ADR-002 for the constraint this places on reactive call sites.

## Implementation Notes

```java
// ProductEntity — version column
@Version
@Column(name = "version", nullable = false)
private Integer version;

// InventoryService — annotated method
@Transactional(isolation = Isolation.REPEATABLE_READ)
@Retryable(on = OptimisticLockException.class, maxAttempts = 3, delayMs = 50)
public void reserveInventory(List<OrderItemCommand> items) { ... }
```

Verification: `DB-3 Test 2` in `04-database.md` — run via Testcontainers to
confirm `REPEATABLE_READ` is actually enforced (not silently overridden by
proxy-through-`this` invocation issues).

TEST-4 (`ConcurrentInventoryTest`) is the acceptance gate: 50 threads, 5 units
each, 100-unit stock. Final inventory must be ≥ 0. Must pass 5 times in a row.
